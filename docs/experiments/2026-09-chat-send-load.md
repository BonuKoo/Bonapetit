# 채팅 발송 부하 측정 — 2026-09-01

이 프로젝트의 **첫 부하 수치**입니다. 그전에는 `application-prod.yml`의 Tomcat 스레드 50 · Hikari 20이 근거 없는 잠정값이었고, "k6 재측정 후 조정" 주석만 달려 있었습니다.

## 측정 방법

`ChatSendLoadTest`(부하 하니스). 브라우저가 하는 것과 같은 경로를 지납니다 — 세션 로그인 → SockJS 핸드셰이크 → STOMP CONNECT → SUBSCRIBE → SEND. 왕복 지연은 **보낸 메시지가 구독으로 되돌아온 시각**으로 잽니다.

```bash
docker run -d --name eatmate-redis -p 6379:6379 redis
./gradlew test --tests "*ChatSendLoadTest" -Dloadtest=true -Dloadtest.users=20 -Dloadtest.messages=50
```

| 항목 | 값 |
|---|---|
| 장비 | i7-6700 (4코어 8스레드) · RAM 16GB |
| DB | **인메모리 H2** |
| Redis | Docker 컨테이너 (실제) |
| 발송 간격 | 사용자당 50ms |
| 방 | 하나. 모든 사용자가 같은 방 |

## 결과

| 동시 사용자 | 인당 메시지 | 처리량 | p50 | p95 | p99 | 유실 |
|---|---|---|---|---|---|---|
| 5 | 10 | 14.7 msg/s | 194 ms | 351 ms | 379 ms | 0 |
| 10 | 50 | 76.7 msg/s | 256 ms | 529 ms | 641 ms | 0 |
| 20 | 50 | 137.8 msg/s | **1,707 ms** | 1,901 ms | 1,946 ms | 0 |

> 사용자 5는 총 50건뿐이라 JIT·연결 준비가 지배합니다. 추세 판단에서는 제외하십시오.

## 읽는 법

**10 → 20에서 꺾입니다.** 사용자가 2배가 되는 동안 처리량은 1.8배(76.7 → 137.8)에 그치는데 **p50은 6.7배**(256ms → 1,707ms)로 뜁니다. 처리량이 평평해지면서 대기가 쌓이는, 전형적인 포화입니다.

**유실은 없습니다.** 세 번 모두 보낸 만큼 응답이 오고 DB 저장 건수도 정확히 일치합니다. 느려질 뿐 메시지가 사라지지는 않습니다.

## 여기서 말할 수 있는 것

**DB가 병목이 아닙니다.** 인메모리 H2인데도 포화했습니다. 디스크 DB로 바꾸면 더 나빠지겠지만, **지금 꺾이는 지점을 만드는 것은 DB가 아닙니다.**

이건 남은 성능 후보의 우선순위를 바꿉니다. "발송 경로에서 계정 SELECT 1건 제거"(JWT에 accountId 싣기)는 **DB 왕복을 줄이는 개선**입니다. 병목이 DB가 아니라면 효과가 크지 않을 가능성이 높습니다.

**의심 가는 곳은 팬아웃입니다.** 한 방에 20명이면 메시지 1건이 20명에게 나갑니다. 1,000건을 보내면 **20,000건이 나갑니다.** 사용자 수에 비례해 커집니다.

```
SEND 1건 → Redis PUBLISH → RedisSubscriber → SimpleBroker → 구독자 N명에게 프레임 N개
```

`architecture.md`가 지적한 **Pub/Sub 단일 채널** 문제와도 겹칩니다. 모든 방의 메시지가 한 채널로 흐르므로 인스턴스마다 무관한 방까지 역직렬화합니다.

## 여기서 말할 수 없는 것

**절대 수치.** 생성기와 서버가 **같은 JVM**입니다. 4코어 장비에서 20개 사용자 스레드가 Tomcat·Redis 클라이언트·H2와 CPU를 나눠 씁니다. 게다가 클라이언트도 20,000개 프레임을 파싱합니다. **실제 서버 용량은 이보다 높습니다.** 이 숫자를 운영 용량으로 읽으면 안 됩니다.

**운영 DB 기준 수치.** H2입니다. 이 프로젝트는 H2와 MySQL의 실행 계획이 갈려 결론이 뒤집힌 적이 있습니다(→ [작업 기록](../worklog-2026-08.md)).

**Tomcat 스레드 50이 맞는지.** WebSocket 연결은 Tomcat 요청 스레드를 오래 잡지 않습니다. 이 측정으로는 그 값을 판단할 수 없습니다.

## 다음에 할 것

1. **생성기를 별도 JVM으로 분리** — 절대 수치를 얻으려면 이게 먼저입니다. 지금 구조로는 클라이언트 비용이 섞입니다
2. **팬아웃 비용 분리 측정** — 방 하나에 N명 vs 방 N개에 1명씩. 같은 총 메시지 수로 비교하면 팬아웃이 원인인지 갈립니다
3. **MySQL로 재측정** — DB가 병목이 아니라는 결론이 디스크 DB에서도 유지되는지
4. 그 뒤에야 **발송 경로 SELECT 제거**를 판단

## 재현

측정 코드는 `src/test/java/com/eatmate/loadtest/`에 있습니다. 운영 코드는 건드리지 않았습니다.

| 파일 | 역할 |
|---|---|
| `ChatSendLoadTest` | 부하 시나리오와 집계 |
| `LoadTestSecurityConfig` | 테스트 스코프 로그인. `/test-only/**`에만 걸리는 체인을 앞에 두고, 그 밖의 경로는 운영 보안 설정을 그대로 지납니다 |
| `LoadStats` | 백분위 집계 |
| `HandshakeProbeTest` | 핸드셰이크가 막힐 때 단계별 상태 코드를 찍는 진단용 |

`-Dloadtest=true`가 없으면 실행되지 않습니다. 일반 `./gradlew test`에서는 건너뜁니다.

### 하니스를 만들며 걸린 것

| 증상 | 원인 |
|---|---|
| 컨텍스트 기동 실패 `Ambiguous mapping` | 중첩 `@RestController`는 설정 클래스 멤버로 자동 등록된다. `@Bean`으로 또 등록하면 핸들러 매핑이 중복된다 |
| 핸드셰이크가 101 대신 200 | 세션 쿠키 이름이 `JSESSIONID`가 아니라 **`SESSION`**(값은 base64). 클래스패스에 `spring-session-data-redis`가 있어 세션이 Redis에 저장된다. **쿠키 이름을 짐작하지 말고 `Set-Cookie`를 그대로 되돌려 보낼 것** |
| `-Dloadtest=true`가 안 먹음 | `-D`는 Gradle JVM에 붙는다. `build.gradle`의 test 태스크가 `loadtest*` 프로퍼티를 테스트 JVM으로 넘겨야 한다 |
