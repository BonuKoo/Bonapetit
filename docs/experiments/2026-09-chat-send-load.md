# 채팅 발송 부하 측정

| 항목 | 값 |
|---|---|
| 측정일 | 2026-09-01 |
| 대상 | 실시간 채팅 발송 경로 (STOMP SEND → 저장 → 구독자 전달) |
| 하니스 | `src/test/java/com/eatmate/loadtest/` |

---

## 1. 테스트 배경

**이 프로젝트에는 부하 수치가 하나도 없었습니다.**

`application-prod.yml`의 두 값이 그 상태를 그대로 보여줍니다.

```yaml
hikari:
  maximum-pool-size: 20   # 시작값 — k6 재측정 후 조정할 것
tomcat:
  threads:
    max: 50               # 시작값 — k6 재측정 후 조정할 것
```

주석에 "재측정 후 조정"이라 적혀 있지만 그 재측정이 없었습니다. 두 값 모두 근거 없이 정해진 채로 운영에 들어가 있었습니다.

채팅은 이 저장소에서 **가장 밀도가 높은 도메인**입니다. 메시지 영속화, 커서 페이징, Redis 캐시, Pub/Sub 다중 인스턴스 전파가 모두 여기 모여 있습니다. 그런데 그 경로가 한 번도 부하 아래에서 측정된 적이 없었습니다.

부하 도구가 없었던 데는 이유가 있습니다. **STOMP를 기본 지원하는 부하 도구가 없습니다.** k6 · Gatling · JMeter 모두 프레임을 수작업으로 조립해야 합니다. 그래서 `WebSocketStompClient` 기반으로 직접 만들어야 했습니다.

---

## 2. 테스트 이유

**무엇을 고칠지 정하기 위해서입니다.**

성능 개선 후보가 넷 남아 있었는데, 전부 "쌀 것 같아서" 수준이었습니다.

| 후보 | 근거 |
|---|---|
| 발송 경로의 계정 SELECT 제거 | 메시지마다 SELECT 1건. **병목인지는 모름** |
| [ISS-14](../known-issues.md#iss-14) 채팅 인가 3 → 2쿼리 | 쿼리 1건 감소. **효과는 모름** |
| 모임 검색 `LIKE %키워드%` | 인덱스 못 씀. **실사용 규모를 모름** |
| Pub/Sub 단일 채널 | 방 수에 비례. **다중 인스턴스가 아님** |

근거 없이 고르면 **안 고쳐도 될 것을 고칩니다.** 실제로 이 프로젝트에서는 그런 일이 이미 세 번 있었습니다 — 코드를 읽어 센 쿼리 수가 실제와 달랐던 사례입니다(인가 1→4, 목록 21→42, 공지 카테시안 곱 의심→정상).

구체적으로 답하고 싶었던 질문은 셋이었습니다.

1. **발송 경로가 병목인가?** 그래야 계정 SELECT 제거가 값이 있습니다
2. **어디서 꺾이나?** 동시 사용자 몇 명부터 체감이 나빠지는가
3. **부하 아래에서 메시지가 유실되나?** [ADR-002](../decisions.md#adr-002-메시지를-동기-insert로-저장한다)는 "정합성 우선, 저장 실패 시 발행도 중단"을 택했습니다. 그 선택이 실제로 지켜지는지

## 3. 테스트 과정

### 3.1 진입 장벽은 성능이 아니라 인증이었습니다

메시지 한 건을 보내려면 네 관문을 지나야 합니다.

| 단계 | 필요한 것 |
|---|---|
| `/ws-stomp` 핸드셰이크 | **인증된 HTTP 세션** |
| STOMP CONNECT | JWT |
| SUBSCRIBE | 핸드셰이크 세션의 `simpUser` + **멤버십** |
| SEND | JWT |

JWT는 시크릿을 알면 만들 수 있습니다. 문제는 세션이었습니다. 소셜 로그인은 스크립트로 통과할 수 없고, 남은 후보는 폼 로그인뿐이었습니다.

**폼 로그인도 쓸 수 없었습니다.** 재 보니 로그인에 성공해도 앱이 그 사용자를 식별하지 못했습니다.

```
principal.getName() → "com.eatmate.security.dto.AuthenticateAccountDto@1a2b3c4d"
```

이 앱은 어디서나 `principal.getName()`을 oauth2Id로 취급하는데, `CustomAuthenticationProvider`가 principal 자리에 `UserDetails`가 아닌 DTO를 넣습니다. 부하 테스트를 만들려다 나온 발견이라 [ISS-09](../known-issues.md#iss-09)를 ⚪낮음에서 🟡중간으로 올렸습니다. 안 쓰는 코드가 아니라 **테스트의 진입로를 막는 항목**이기 때문입니다.

### 3.2 테스트 전용 로그인 — 어디까지 우회할 것인가

`/test-only/**`에만 걸리는 보안 체인을 **하나 더 앞에** 두고, 거기서만 세션을 만듭니다.

```
/test-only/**   → 테스트 체인 (permitAll)
그 밖의 모든 것 → 운영 SecurityConfig 그대로
```

**핸드셰이크 인가는 실제 필터 체인을 지나게 두었습니다.** 그것까지 우회하면 측정 경로가 실제와 달라집니다. 우회는 "로그인하는 방법"에만 적용하고, "인가되는지"는 실제 코드가 판단하게 했습니다.

`@TestConfiguration`이라 컴포넌트 스캔에 걸리지 않고, 쓰려는 테스트가 `@Import`로 명시해야 켜집니다. **`src/main`은 한 줄도 바꾸지 않았습니다.**

### 3.3 만들며 걸린 것

| 증상 | 원인 |
|---|---|
| 컨텍스트 기동 실패 `Ambiguous mapping` | 중첩 `@RestController`는 설정 클래스 멤버로 자동 등록된다. `@Bean`으로 또 등록하면 매핑이 중복된다 |
| 핸드셰이크가 101 대신 **200** | 세션 쿠키가 `JSESSIONID`가 아니라 **`SESSION`**(값은 base64). 클래스패스에 `spring-session-data-redis`가 있어 세션이 Redis에 저장된다 |
| `-Dloadtest=true`가 안 먹음 | `-D`는 Gradle JVM에 붙는다. test 태스크가 테스트 JVM으로 넘겨야 한다 |

두 번째는 추측으로 못 찾았습니다. **단계별 상태 코드를 찍는 진단 테스트**(`HandshakeProbeTest`)를 따로 만들어서 잡았습니다.

```
1) /test-only/login   200  Set-Cookie = SESSION=ODJhYzlmZWMt...   ← JSESSIONID가 아니었다
2) /chat/rooms        200  로그인페이지로 튕겼나=false
3) /ws-stomp/info     200  {"websocket":true}
4) /ws-stomp/websocket 400 Can "Upgrade" only to "WebSocket"      ← 엔드포인트는 정상
```

### 3.4 1차 — 어디서 꺾이나

동시 사용자를 늘려가며 왕복 지연을 쟀습니다. 지연은 **보낸 메시지가 구독으로 되돌아온 시각**으로 잽니다.

| 항목 | 값 |
|---|---|
| 장비 | i7-6700 (4코어 8스레드) · RAM 16GB |
| DB | **인메모리 H2** |
| Redis | Docker 컨테이너 (실제) |
| 발송 간격 | 사용자당 50ms |
| 방 | 하나. 모든 사용자가 같은 방 |

### 3.5 2차 — 교란변수를 분리한다

1차 결과만으로는 원인이 갈리지 않았습니다. 후보가 둘이었는데 **둘 다 전달 건수를 따라 움직이기** 때문입니다.

- **팬아웃** — 한 방에 N명이면 메시지 1건이 N명에게 나간다
- **클라이언트 비용** — 생성기가 서버와 같은 JVM이라 프레임 파싱이 CPU를 나눠 쓴다

**보낸 건수를 고정한 채 전달 건수만 바꾸면 갈립니다.** 세 시나리오를 같은 JVM에서 연달아 돌렸습니다(워밍업 상태를 맞추려고, 앞에 버리는 실행을 하나 넣었습니다).

```
한 방 N명    보냄 600 → 전달 600×N   (지금 구조)
N방 1명씩    보냄 600 → 전달 600     (팬아웃 없음)
구독 없음    보냄 600 → 전달 0       (순수 수신 처리)
```

지연은 세 시나리오를 한 자로 잴 수 없습니다(구독 없는 쪽은 왕복이 없습니다). 그래서 공통 지표를 **첫 발송부터 DB에 전부 저장될 때까지의 시간**으로 잡았습니다. 서버가 실제로 일을 끝낸 시점입니다.

## 4. 테스트 결과

### 4.1 1차 — 10에서 20 사이에 꺾인다

| 동시 사용자 | 인당 메시지 | 처리량 | p50 | p95 | p99 | 유실 |
|---|---|---|---|---|---|---|
| 5 | 10 | 14.7 msg/s | 194 ms | 351 ms | 379 ms | 0 |
| 10 | 50 | 76.7 msg/s | 256 ms | 529 ms | 641 ms | 0 |
| 20 | 50 | 137.8 msg/s | **1,707 ms** | 1,901 ms | 1,946 ms | 0 |

> 사용자 5는 총 50건뿐이라 JIT·연결 준비가 지배합니다. 추세 판단에서는 제외하십시오.

사용자가 2배가 되는 동안 처리량은 1.8배(76.7 → 137.8)에 그치는데 **p50은 6.7배**(256ms → 1,707ms)로 뜁니다. 처리량이 평평해지면서 대기가 쌓이는, 전형적인 포화입니다.

**유실은 없었습니다.** 세 번 모두 보낸 만큼 응답이 오고 DB 저장 건수가 정확히 일치했습니다. 질문 3의 답입니다 — 느려질 뿐 메시지가 사라지지는 않습니다. ADR-002의 선택이 부하 아래에서도 지켜집니다.

### 4.2 2차 — 팬아웃이 맞다

사용자 20 · 인당 30건 · **세 시나리오 모두 보낸 건수 600으로 동일**

| 시나리오 | 보냄 | 전달 | 저장 완료 | 처리량 | p50 | p95 |
|---|---|---|---|---|---|---|
| 한 방 20명 | 600 | **12,378** | 2,984 ms | 201.1/s | **277 ms** | 482 ms |
| 20방 1명씩 | 600 | 622 | 1,858 ms | 322.9/s | **23 ms** | 70 ms |
| 구독 없음 | 600 | 0 | 1,853 ms | 323.8/s | — | — |

> 전달이 12,000이 아니라 12,378인 것은 입장 알림 때문입니다. 20명이 한 방에 들어오면 k번째 입장이 k명에게 전달돼 210건이 더해집니다.

**같은 600건을 보냈는데 지연이 277ms 대 23ms, 12배입니다.** 다른 조건은 전부 같고 전달 건수만 20배 차이입니다.

**전달이 적으면 팬아웃 유무가 무의미합니다.** 「20방 1명씩」(1,858ms)과 「구독 없음」(1,853ms)이 사실상 같습니다. 622건을 전달하는 비용은 0에 가깝습니다. 비용은 *"전달한다"*가 아니라 **"전달량이 커진다"**에서 옵니다.

**뒤의 두 시나리오는 포화하지 않았습니다.** 발송 간격 50ms × 30건이면 발송 창이 약 1.5초인데 1.85초에 저장이 끝났습니다. 서버가 들어오는 속도를 따라갔다는 뜻입니다. 322.9/s는 **한계가 아니라 걸어준 부하**입니다. 한 방 시나리오만 발송이 끝난 뒤로도 1.5초를 더 썼습니다.

### 4.3 질문에 대한 답

| 질문 | 답 |
|---|---|
| 발송 경로가 병목인가 | **아니다.** 인메모리 H2인데도 포화했고, 세 시나리오의 발송 경로는 완전히 같은데 차이는 전부 전달 쪽에서 났다 |
| 어디서 꺾이나 | 이 환경에서 **동시 사용자 10~20 사이**. 단, 아래 한계 참조 |
| 유실이 있나 | **없다.** 모든 측정에서 보낸 만큼 저장됐다 |

### 4.4 여기서 말할 수 없는 것

**절대 수치.** 생성기와 서버가 **같은 JVM**입니다. 4코어 장비에서 20개 사용자 스레드가 Tomcat·Redis 클라이언트·H2와 CPU를 나눠 쓰고, 클라이언트도 12,378개 프레임을 파싱합니다. 실제 운영에서는 브라우저가 각자 다른 기기에 있으니 **체감은 이 수치보다 낫습니다.** 이 숫자를 운영 용량으로 읽으면 안 됩니다.

다만 **서버가 메시지 1건마다 N번 써야 한다**는 구조는 기기를 나눠도 사라지지 않습니다.

**운영 DB 기준 수치.** H2입니다. 이 프로젝트는 H2와 MySQL의 실행 계획이 갈려 결론이 뒤집힌 적이 있습니다.

**Tomcat 스레드 50이 맞는지.** WebSocket 연결은 Tomcat 요청 스레드를 오래 잡지 않습니다. 이 측정으로는 그 값을 판단할 수 없습니다. **`application-prod.yml`의 두 잠정값은 여전히 잠정값입니다.**

## 5. 테스트 의의

### 5.1 고칠 대상이 바뀌었다

측정 전 1순위는 **"발송 경로에서 계정 SELECT 1건 제거"**(JWT에 accountId를 실어 `getReferenceById` 사용)였습니다. 메시지마다 나가는 쿼리라 값이 커 보였습니다.

두 번의 측정이 연달아 그것을 뒤로 밀었습니다.

| | 발견 | 함의 |
|---|---|---|
| 1차 | 인메모리 H2인데도 포화 | DB가 병목이 아니다 |
| 2차 | 발송 경로가 동일한데 지연이 12배 갈림 | 차이는 전부 전달 쪽 |

**재기 전이었으면 안 고쳐도 될 것을 고쳤을 겁니다.** 이 프로젝트에서 "읽어서 센 것"과 "실측"이 갈린 **네 번째** 사례입니다.

| 대상 | 읽어서 | 실측 |
|---|---|---|
| 인가 검사 쿼리 | 1건 | **4건** |
| 모임 목록 쿼리 | 21건 | **42건** |
| 공지 검색 조인 | 카테시안 곱 의심 | **정상** |
| 채팅 병목 | 발송 경로 DB | **팬아웃** |

### 5.2 최적화하지 않을 근거도 생겼다

측정이 알려준 것 중 실행에 옮기기 전에 멈춰야 할 것이 있습니다.

**팬아웃 최적화는 아직 착수 대상이 아닙니다.** 지금 수치는 "한 방 20명"이라는 **임의로 정한 조건**에서 나왔습니다. 이 서비스는 식사 모임이고, 실제 모임 인원이 4~6명이라면 전달량은 지금의 1/4 이하이고 **최적화할 대상 자체가 없습니다.**

다음에 필요한 것은 코드가 아니라 서비스 쪽 사실입니다 — **실제 모임당 인원 분포.** 그게 정해지면 그 크기로 다시 재서 판단하면 됩니다.

성능 작업에서 "무엇을 고칠까"만큼 "무엇을 안 고쳐도 되나"가 중요한데, 측정 없이는 후자를 말할 수 없습니다.

### 5.3 다음 사람이 이어받을 수 있다

수치보다 오래 남는 것은 하니스입니다. 명령 한 줄로 재현되고, 개선 전후 비교에 그대로 쓸 수 있습니다.

```bash
docker run -d --name eatmate-redis -p 6379:6379 redis
./gradlew test --tests "*ChatSendLoadTest" -Dloadtest=true -Dloadtest.users=20 -Dloadtest.messages=50
./gradlew test --tests "*ChatFanoutLoadTest" -Dloadtest=true
```

| 파일 | 역할 |
|---|---|
| `ChatSendLoadTest` | 1차 — 동시 사용자를 늘리며 포화 지점을 본다 |
| `ChatFanoutLoadTest` | 2차 — 보낸 건수를 고정하고 전달 건수만 바꾼다 |
| `LoadTestSecurityConfig` | 테스트 스코프 로그인. `/test-only/**`에만 걸리는 체인 |
| `LoadStats` | 백분위 집계 |
| `HandshakeProbeTest` | 핸드셰이크가 막힐 때 단계별 상태 코드 진단 |

`-Dloadtest=true`가 없으면 실행되지 않습니다. Redis가 필요하고 수십 초가 걸려 일반 `./gradlew test`에 섞이면 안 되기 때문입니다.

### 5.4 남은 것

순서에 근거가 있습니다. 위에서부터 **지금 결론에서 가장 흐린 것**을 걷어내는 순입니다.

1. **생성기를 별도 JVM으로 분리** — 클라이언트 파싱 비용을 걷어내야 서버 쪽 팬아웃만 남습니다
2. **실제 방 크기 분포 확인** — 이게 없으면 팬아웃 최적화는 판단할 수 없습니다
3. **MySQL로 재측정** — "DB가 병목이 아니다"가 디스크 DB에서도 유지되는지
4. **발송 경로 SELECT 제거** — 위 셋보다 뒤
