## ADR-001. 메시지 영속화를 발행부에서 수행한다

**상태** 채택

### 맥락

채팅 메시지를 RDBMS에 저장하기로 하면서, 저장 코드를 어디에 둘지 정해야 했습니다. 후보는 두 곳이었습니다.

```
ChatController.message() ──> ChatService.sendChatMessage()   ← 발행부
                                  └─ redisTemplate.convertAndSend()
                                          │
                                          ↓ (구독 중인 모든 인스턴스가 수신)
                                     RedisSubscriber.sendMessage()   ← 수신부
```

### 결정

**발행부(`ChatService`)에서 저장**합니다.

### 근거

Redis Pub/Sub은 구독 중인 **모든 서버 인스턴스**에 메시지를 전달합니다. 수신부에서 저장하면 서버가 N대일 때 같은 메시지가 **N번 저장**됩니다. 발행 지점은 메시지당 정확히 1회만 실행됩니다.

### 결과

- 다중 인스턴스 환경에서도 메시지당 정확히 1행이 저장됩니다
- 발행부가 영속성 책임까지 지게 되어 `ChatService`의 의존성이 늘었습니다(저장소 3개 추가)
- 저장과 발행이 한 트랜잭션에 묶이면서 [ADR-006](#adr-006-캐시는-가용성-영속화는-정합성을-우선한다)의 실패 정책이 따라왔습니다

## ADR-002. 메시지를 동기 INSERT로 저장한다

**상태** 채택

### 맥락

메시지 저장이 실시간 발행 경로에 들어가므로, 저장 방식이 채팅 응답 지연에 영향을 줍니다. 동기 INSERT · 비동기 저장 · Redis 버퍼링 후 배치 삽입을 검토했습니다.

### 결정

**동기 INSERT**로 저장하고, 저장 실패 시 발행도 중단합니다.

### 근거

| 방식 | 문제 |
|---|---|
| 비동기 저장 | 서버가 비정상 종료하면 버퍼에 남은 메시지가 유실됩니다 |
| Redis 버퍼링 + 배치 | 조회가 "아직 내려가지 않은 분량 + DB 분량"에 걸쳐 **커서 페이징이 두 데이터 소스로 쪼개집니다**. [ADR-003](#adr-003-내역-조회에-커서-페이징을-쓰고-page-대신-list를-반환한다)의 경계 계산이 크게 복잡해집니다 |

무엇보다 **병목으로 측정된 바가 없는 상태**였습니다. 이미 메시지당 Redis 왕복이 여러 번 일어나고 있어, 인덱스가 걸린 단순 INSERT 1회는 같은 자릿수의 비용입니다.

### 결과

- 저장 실패가 곧 발행 실패입니다. DB 장애 시 채팅이 동작하지 않습니다
- 대신 화면에는 보이는데 내역에는 없는 메시지가 생기지 않습니다
- 나중에 부하 측정에서 병목으로 확인되면 `ChatService` 한 곳만 고치면 되는 국소 변경입니다
- 곁들여 중복 `getUserCount` 호출을 제거해, INSERT 1회 추가분이 사실상 상쇄됐습니다

## ADR-003. 내역 조회에 커서 페이징을 쓰고 `Page` 대신 `List`를 반환한다

**상태** 채택

### 맥락

채팅 내역은 최신부터 거슬러 올라가며 조회합니다. 새 메시지가 계속 들어오는 중에도 페이지 경계가 밀리지 않아야 합니다.

### 결정

- 커서 기반 페이징. 정렬·커서 키는 **`id`**
- 커서 비교는 **배타적(`<`)**
- 저장소는 `Page`가 아니라 **`List` + `Pageable`**(limit 용도)을 반환
- 다음 페이지 존재 여부는 **`size+1`건 조회**로 판정
- `(room_id, chat_message_id)` 복합 인덱스

### 근거

| 항목 | 이유 |
|---|---|
| 커서 키 `id` | `createdAt`은 같은 밀리초에 여러 건이 들어올 수 있어 커서로 부적합합니다 |
| 배타적 경계 | `<=`로 두면 페이지마다 1건씩 중복됩니다 |
| `Page` 미사용 | `Page`는 매 요청마다 `count(*)`를 추가 실행합니다. 채팅 내역에 전체 건수는 필요 없습니다 |
| `size+1` 판정 | count 쿼리 없이 다음 페이지 유무를 알 수 있습니다 |
| QueryDSL 미사용 | 조건이 고정 2개뿐이라 오버엔지니어링입니다. 기존 `NoticeRepository4QueryDsl`은 동적 검색 때문에 도입한 것입니다 |

### 결과

- 전체 건수와 전체 페이지 수를 표시할 수 없습니다. 채팅 UI에는 필요 없다고 판단했습니다
- 실사용 234건으로 경계를 검증했습니다 — 5페이지 합계 234건, 중복·누락 0
- 복합 인덱스의 실제 기여를 MySQL에서 측정했습니다. 인덱스가 없으면 51건을 얻는 데 1,016행을 읽습니다(0.623 ms → 0.116 ms)

## ADR-004. 설정을 공통/dev/prod 3파일로 분리한다

**상태** 채택

### 맥락

단일 `application.yml` 안에서 `---` 문서 겹침으로 환경을 나누고 있었습니다. 이 구조가 두 가지 문제를 낳았습니다.

- 브랜치마다 같은 파일이 다르게 진화해 병합할 때마다 충돌했습니다. **실제로 1년간 방치된 충돌의 원인**이었습니다
- 운영 문서가 기본(개발) 문서 위에 얹히는 구조라, 운영이 덮어쓰지 않은 개발용 설정이 **운영으로 새어 들어갔습니다**

### 결정

`application.yml`(공통) + `application-dev.yml` + `application-prod.yml`로 분리하고, **세 파일 모두 모든 브랜치에 동일하게** 둡니다. 환경 선택은 `SPRING_PROFILES_ACTIVE`로 하며 미지정 시 `dev`입니다.

브랜치별로 다른 설정 파일을 두는 방식은 채택하지 않았습니다. 그렇게 하면 브랜치 병합마다 설정 충돌이 반복되는데, 그게 애초에 이 문제의 원인이었기 때문입니다.

### 근거

환경 차이가 파일 경계로 고정되고 공통부가 한 곳에만 존재하면, 어느 브랜치로 병합하든 설정 파일이 충돌하지 않습니다.

### 결과

- 분리 후 원본과 프로퍼티 단위로 대조해 동작 동등성을 확인했습니다(dev 차이 0건, prod 차이 4건 — 모두 바인딩되지 않는 죽은 키)
- 419줄 1파일 → 283줄 3파일
- 로컬 실행에 환경변수 6개가 필요했던 문제는 dev 프로필에만 더미 fallback을 넣어 해소했습니다. 운영은 공통 설정의 `${...}`(fallback 없음)를 그대로 상속하므로 여전히 엄격합니다

## ADR-005. 방 진입 경로를 캐싱한다 (첫 페이지 + 멤버십)

**상태** 채택 — **근거의 일부는 이후 철회됨**

### 맥락

"채팅방에 들어왔을 때 대화를 빠르게 읽고 싶다"는 요구에서 출발했습니다. 캐시를 넣기 전에 무엇이 비용인지 측정했습니다.

Hibernate `Statistics`로 실제 쿼리 수를 셌습니다.

| 상황 | 쿼리 수 |
|---|---|
| 캐시 없음 | **4** (방 조회 · 계정 조회 · 멤버십 조회 · 메시지 조회) |
| 멤버십만 캐시 | **1** |
| 둘 다 캐시 | **0** |

**4건 중 3건이 인가 검증**이었습니다.

### 결정

| 키 | 자료구조 | 용도 | TTL |
|---|---|---|---|
| `CHAT_RECENT:{roomId}` | List (최대 101) | 방 진입 시 읽는 최신 메시지 | 1일 |
| `CHAT_AUTH:{roomId}:{oauth2Id}` | String | 멤버십 검증 결과 | 5분 |

- **첫 페이지만 캐싱**합니다. 위로 스크롤하는 구간은 항상 DB입니다
- 용량은 **101**입니다(조회 상한 100 + 다음 페이지 판정용 1건)
- 갱신은 **LPUSHX**로 하여 키가 있을 때만 밀어 넣습니다
- **멤버로 확인된 경우만** 캐싱합니다
- 탈퇴·강퇴 시 `PostTeamService.kickMember`에서 **즉시 무효화**합니다

### 근거

| 결정 | 이유 |
|---|---|
| 첫 페이지만 | 캐시/DB 경계가 `before` 유무 하나로 명확해져, 두 소스에 걸친 커서 계산을 피합니다 |
| 용량 101 | 100이면 `size=100` 요청만 캐시를 못 타는 어정쩡한 구멍이 생깁니다 |
| LPUSHX | 키가 없는데 push하면 최신 몇 건만 든 반쪽짜리 캐시가 만들어져, 이후 조회가 "더 이전 메시지가 없다"고 잘못 판단합니다. 캐시는 반드시 통째로 채워야 "캐시 길이 < 용량"이 "실제로 그만큼뿐"을 의미합니다 |
| 멤버만 캐싱 | 비멤버까지 캐싱하면 방금 참여한 사용자가 TTL이 끝날 때까지 차단됩니다 |
| 즉시 무효화 | 권한을 **빼앗는** 작업이라 TTL 만료를 기다리면 그 사이 조회가 계속 통과합니다. TTL 5분은 이 경로를 놓쳤을 때의 안전망입니다 |

### 철회된 근거

처음에는 **메시지 캐싱 자체에도 성능 근거가 있다**고 판단했습니다. 개발용 H2에서 `EXPLAIN ANALYZE`를 돌린 결과가 이랬기 때문입니다.

```
-- H2 · 첫 페이지 (방에 메시지 234건)
/* IDX_CHAT_MESSAGE_ROOM_ID: ROOM_ID = '...' */
/* scanCount: 235 */          ← 방의 메시지를 전부 읽고 정렬
```

"첫 페이지 조회가 방 크기에 비례해 느려진다"고 결론 냈습니다. **MySQL 8.4에 동일 스키마를 만들고 11만 건으로 재측정하니 뒤집혔습니다.**

```
-- MySQL · 같은 쿼리 (방에 메시지 5,000건 / 테이블 전체 11만 건)
-> Limit: 51 row(s)  (actual time=0.017..0.107 rows=51 loops=1)
    -> Index lookup using idx_chat_message_room_id (room_id='bulk-7') (reverse)
       (cost=1053 rows=5000) (actual rows=51 loops=1)
```

MySQL은 복합 인덱스를 역방향으로 스캔하며 `LIMIT`에서 조기 종료합니다. 방 크기와 무관하게 51행만 읽습니다. **H2에서 본 전체 스캔은 H2 옵티마이저의 한계**였지 쿼리 설계 문제가 아니었습니다.

따라서 **메시지 캐싱의 성능 근거는 철회**합니다. 운영 환경에서 메시지 조회는 51행 · 0.1 ms 수준입니다.

### 결과

- 캐시의 실질적 가치는 **인가 검증 3쿼리 제거**입니다. 메시지 캐싱은 왕복 1회를 더 줄이는 부수 효과입니다
- 메시지 캐싱을 되돌리지는 않았습니다. 구현과 실패 격리가 이미 끝났고, 제거하면 메시지 쿼리 1건이 남기 때문입니다
- `ChatHistoryQueryCountTest`가 쿼리 수 4 → 1 → 0을 회귀 테스트로 고정합니다
- **교훈** — 성능 판단은 운영 DB에서 해야 합니다. 개발 DB만 보고 결론 내면 틀립니다

## ADR-006. 캐시는 가용성, 영속화는 정합성을 우선한다

**상태** 채택

### 맥락

같은 Redis를 쓰지만 메시지 영속화와 방 진입 캐시는 성격이 다릅니다. 실패했을 때 어떻게 할지를 각각 정해야 했습니다.

### 결정

실패 정책을 **의도적으로 반대**로 둡니다.

| | 실패 시 |
|---|---|
| 메시지 영속화 | 예외 전파 → **발행까지 중단** |
| 방 진입 캐시 | 예외 삼킴 → **DB로 폴백** |

특히 **멤버십 캐시 조회 실패는 반드시 `false`를 반환**합니다.

### 근거

영속화가 실패했는데 발행하면, 화면에는 보이지만 내역에는 없는 메시지가 생깁니다. 정합성이 깨집니다.

반대로 캐시 예외가 전파되면 **Redis 장애가 곧 채팅 조회 장애**가 됩니다. 캐시는 없어도 DB로 답할 수 있으므로 서비스를 멈출 이유가 없습니다.

멤버십 조회가 실패했을 때 `true`를 반환하면 **Redis 장애가 인가 우회로 이어집니다.** 이건 성능이 아니라 보안 문제입니다.

### 결과

- `ChatCacheRepository`의 모든 Redis 접근이 try-catch로 감싸여 있습니다
- 갱신에 실패하면 낡은 캐시를 남기지 않고 해당 방 캐시를 폐기합니다. 캐시가 뒤처지면 낡은 첫 페이지를 보여주게 되기 때문입니다
- 이 계약을 테스트 6건(`ChatCacheRepositoryTest`의 실패 격리 절)으로 고정했습니다

## ADR-007. 채팅 도메인의 읽기와 쓰기를 분리한다

**상태** 채택

### 맥락

`ChatService` 하나가 메시지 발행 · 영속화 · 내역 조회 · 인가 검증 · 커서 계산을 모두 맡으면서 커지고 있었습니다.

### 결정

- `ChatService` — 발행과 영속화 (쓰기)
- `ChatHistoryService` — 내역 조회, 인가, 커서 계산 (읽기)

### 근거

두 경로는 트랜잭션 성격(`@Transactional` vs `readOnly`), 실패 정책([ADR-006](#adr-006-캐시는-가용성-영속화는-정합성을-우선한다)), 의존하는 저장소가 모두 다릅니다. 한 클래스에 두면 어느 쪽 규칙이 적용되는지가 코드에서 드러나지 않습니다.

### 결과

- 각 클래스의 테스트가 독립적입니다(쓰기 8건 / 읽기 17건)
- 캐시 도입 시 읽기·쓰기 경로에 각각 다른 캐시 연산을 붙이기 쉬웠습니다
- 클래스가 하나 늘었습니다
