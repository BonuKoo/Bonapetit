# 문제 해결

## 1. 로그인만 하면 남의 모임을 조작할 수 있었다

**PR** [#76](https://github.com/BonuKoo/Bonapetit/pull/76) · **이슈** [ISS-01](known-issues.md#iss-01) 🔴 치명

### 문제 인식

인수인계 문서에 "인가 검증 누락"이 1순위로 적혀 있었습니다. 코드를 읽어 보니 **다섯 갈래**였고, 전부 같은 모양이었습니다.

```
"누구를"을 요청 파라미터에서 읽고 세션 주체와 대조하지 않는다
```

화면이 자기 값을 채워 보낼 뿐 서버는 확인하지 않았습니다. 값을 바꿔 보내면 그대로 통했습니다.

| 지점 | 결과 |
|---|---|
| `PostController` 수정·삭제·강퇴·수정화면·팀원목록 | 로그인만 하면 임의의 `teamId`로 남의 모임 조작 |
| `AccountProfileController.leaveTeam` | 남의 `account_id`로 그 사람을 모임에서 제외 |
| `ChatRoomController.enterRoom` | 타 모임의 `roomId`·방 이름 노출 |
| `StompHandler` SUBSCRIBE | `roomId`만 알면 남의 대화를 실시간 열람 |

**목록에 없던 것을 하나 더 찾았습니다.** `leaveTeam`을 고치다 같은 파일에서 `deleteAccount`를 봤는데, `oauth2_id`를 요청에서 받아 그대로 삭제하고 있었습니다. **남의 식별자를 넣으면 그 계정이 지워집니다.** 같은 결함이고 피해가 더 커서 함께 고쳤습니다.

### 해결 과정

다섯 곳에 같은 검사를 복사하면 한 곳만 빠뜨려도 곧 구멍입니다. **검사를 협력자 둘에 모았습니다.**

| 협력자 | 기준 | 쓰는 곳 |
|---|---|---|
| `TeamAccessService` | teamId | 모임 관리, 탈퇴, 채팅방 진입 |
| `ChatRoomMembershipVerifier` | roomId | 내역 조회, STOMP 구독 |

두 번째는 `ChatHistoryService`의 private 메서드를 꺼낸 것입니다. HTTP 조회와 STOMP 구독이 **같은 코드를 쓰지 않으면 한쪽만 고쳐지는 일**이 생기는데, 인가에서는 그게 곧 구멍입니다.

핵심은 검사 방식이 아니라 **결과를 쓰게 만든 것**입니다.

```java
TeamMembership membership = teamAccessService.requireMember(teamId, principal.getName());
postTeamService.kickMember(String.valueOf(membership.accountId()), teamId);
//                                        ^^^^^^^^^^^^^^^^^^^^^ 요청의 account_id가 아니라 이 값
```

검사만 하고 요청의 `account_id`로 처리하면, **검사를 통과한 사람이 남을 탈퇴시킬 수 있습니다.** 반환값을 쓰게 강제하면 그 실수가 구조적으로 막힙니다.

STOMP 쪽은 판단 근거를 골라야 했습니다. CONNECT 헤더의 JWT는 클라이언트가 직접 담는 값이라 쓰지 않고, **핸드셰이크 때 세션에서 넘어온 인증 객체**(`simpUser`)를 썼습니다.

### 결과

- 🔴 치명 이슈가 0건이 됐습니다
- **테스트 50 → 85건.** 늘어난 35건은 전부 인가이며 **계정·모임 도메인에 처음 생긴 자동 검증**입니다
- 거부만이 아니라 **부수효과까지** 검증합니다 — 구독을 막으면서 접속자 수를 올리거나 입장 알림을 발행하면, 막았어도 방에 흔적이 남습니다
- 설계 근거는 [ADR-008](decisions.md#adr-008-인가-검사를-한곳에-모으고-필요한-두-값만-프로젝션한다)에 남겼습니다

## 2. 대화한 사용자는 탈퇴할 수 없었다

**PR** [#79](https://github.com/BonuKoo/Bonapetit/pull/79) · [#80](https://github.com/BonuKoo/Bonapetit/pull/80) · **이슈** [ISS-15](known-issues.md#iss-15) · [ISS-16](known-issues.md#iss-16) 🔴 치명

### 문제 인식

성능을 재려고 `chat_message`의 FK를 살펴보다 발견했습니다. 원래 찾던 것이 아닙니다.

```
ConstraintViolationException: Referential integrity constraint violation
```

`account`를 참조하는 테이블은 셋인데 삭제 경로가 둘만 정리하고 있었습니다.

| 참조 테이블 | 처리 |
|---|---|
| `notice.account_id` | 삭제 ✅ |
| `account_team.account_id` | 삭제 ✅ |
| `chat_message.account_id` | **누락** ❌ |

**메시지를 한 번이라도 보낸 사용자는 회원 탈퇴가 실패합니다.** 실사용자 대부분이 여기 해당합니다.

같은 모양을 의심해 모임 삭제도 재 봤더니 **거기도 걸렸습니다.**

```
CHAT_MESSAGE FOREIGN KEY(ROOM_ID) REFERENCES CHAT_ROOM(ROOM_ID)
```

`Team`은 `cascade = ALL`로 `ChatRoom`까지 지우지만 `ChatRoom`에는 메시지 컬렉션이 없어 **cascade가 `chat_message`까지 닿지 않습니다.**

**둘 다 같은 뿌리입니다.** 메시지 영속화([#70](https://github.com/BonuKoo/Bonapetit/pull/70))로 새 테이블이 생겼는데, **그 테이블을 참조하는 삭제 경로들이 따라오지 않았습니다.**

### 해결 과정

처방이 서로 다릅니다. 컬럼 제약이 다르기 때문입니다.

| | 회원 탈퇴 | 모임 삭제 |
|---|---|---|
| 끊어야 할 FK | `chat_message.account_id` | `chat_message.room_id` |
| 컬럼 | nullable | **`nullable = false`** |
| 처방 | NULL로 연결만 끊고 **대화 보존** | 방과 **함께 삭제** |

탈퇴 쪽 처방은 설계에 이미 답이 있었습니다. `sender`가 nullable이고 표시 이름을 `sender_name` 스냅샷으로 따로 들고 있는 이유가 그것입니다 — **한 사람이 나갔다고 남은 참여자들이 함께 만든 대화가 사라지면 안 됩니다.**

모임 삭제는 반대입니다. 대화의 주인인 모임 자체가 사라지므로 함께 지웁니다. 다만 `@OneToMany(cascade = ALL)`은 쓰지 않았습니다. 그러면 **메시지를 전부 영속성 컨텍스트에 올려 한 건씩** 지워서, 대화가 많은 방일수록 비용이 선형으로 커집니다. `DELETE` 한 문장이면 됩니다.

삭제가 여러 단계가 되면서 컨트롤러에 있던 로직을 서비스로 옮기고 `@Transactional`을 걸었습니다. 중간에 실패해 **메시지만 지워지고 모임이 남는** 상태를 막아야 합니다.

캐시도 함께 걷어냅니다. 모임 삭제는 참여자 **전원에게서** 권한을 빼앗는 작업이라, 강퇴·탈퇴와 같은 이유로 즉시 무효화합니다([ADR-005](decisions.md#adr-005-방-진입-경로를-캐싱한다-첫-페이지--멤버십)). 그러지 않으면 멤버십 캐시가 살아 있는 동안 인가를 통과하고 방 조회를 건너뛰므로 **사라진 모임의 대화가 최대 5분간 계속 읽힙니다.**

### 결과

- 두 경로 모두 정상 동작합니다. 탈퇴해도 대화는 남고 표시 이름은 스냅샷으로 보존됩니다
- **테스트가 서비스를 직접 호출합니다.** 결함이 SQL이 아니라 **서비스가 한 단계를 빠뜨린 것**이었으므로, SQL만 검증하면 같은 실수를 다시 놓칩니다
- **수정을 임시로 되돌려 테스트가 실패하는 것을 확인했습니다.** 통과만 하고 회귀를 못 잡는 테스트가 아닙니다
- 문서를 정정했습니다. `UR-03`과 `UR-12`가 **검증 없이 "✅ 충족"으로 적혀** 있었습니다. UR-12("발신자가 탈퇴해도 메시지는 남는다")는 탈퇴 자체가 실패했으니 확인할 방법도 없었습니다

## 3. 오류가 나면 로그인 페이지로 튕겼다

**PR** [#84](https://github.com/BonuKoo/Bonapetit/pull/84) · **이슈** [ISS-11](known-issues.md#iss-11) 🟡 중간

### 문제 인식

문서에 두 가지가 적혀 있었는데 **재 보니 둘 다 서술이 틀렸습니다.**

| 원래 서술 | 실측 |
|---|---|
| "**크롤러 접근만으로** 삭제될 수 있다" | 크롤러는 못 합니다. `@PreAuthorize("hasRole('ROLE_ADMIN')")`가 걸려 있습니다. 위험 대상은 **관리자 세션**입니다 |
| "오류 응답에 **스택 정보가 포함될 수 있다**" | 포함되지 않습니다. Boot 3 기본값이 `include-stacktrace=never`입니다 |

대신 **문서에 없던 문제**가 나왔습니다.

```
GET /post/detail/999999
  → 302  Location: /login      ← 400도 500도 아니다
```

`/error`가 `permitAll`이 아니라 **오류 디스패치까지 보안 필터에 걸리고** 있었습니다. 비로그인 사용자는 어떤 오류를 만나도 오류 페이지 대신 로그인 화면을 봅니다.

### 해결 과정

세 가지를 고쳤습니다.

| 문제 | 조치 |
|---|---|
| 공지 삭제가 `GET` | `POST`로. 화면의 링크도 폼 전송으로 |
| 없는 id가 500 | `IllegalArgumentException` → 400, `NoSuchElementException` → 404 |
| 오류 시 로그인으로 튕김 | `/error`를 `permitAll`로 |

전역 처리기는 **위 두 예외만** 다룹니다. `AccessDeniedException`은 Spring Security가 403으로 처리하므로 가로채면 그 처리가 망가지고, 나머지는 Boot 기본 500이 맞으며 내부 정보도 새지 않습니다. **포괄 처리기를 두면 예상 못 한 예외를 조용히 삼킬 위험만 생깁니다.**

`sendError`를 쓴 이유는 이 앱이 뷰와 REST가 섞여 있어서입니다. `ResponseEntity`로 직접 응답하면 뷰 요청에 빈 화면이 나갑니다. 오류 디스패치로 넘기면 뷰는 오류 페이지를, REST는 오류 JSON을 받고 **상태 코드만 바로잡힙니다.**

### 결과

- 상태 코드가 맞아졌습니다. 재시도해도 소용없는 요청(400)과 서버 장애(500)가 구분됩니다
- **CSRF는 손대지 않고 [ISS-17](known-issues.md#iss-17)로 분리했습니다.** 켜는 것 자체는 한 줄이지만 axios 두 곳과 **SockJS 폴백 전송**이 딸려 옵니다. `/ws-stomp/**`를 예외로 두지 않으면 WebSocket이 안 되는 환경의 채팅이 끊깁니다. **소셜 로그인을 마친 브라우저로 확인하지 않고 넣으면 안 되는 변경**이라 남겼습니다
- 곁들여 알게 된 것 — **`@WebMvcTest`에서는 `@PreAuthorize`가 동작하지 않습니다.** `@EnableMethodSecurity`가 `SecurityConfig`에 있는데 슬라이스는 그것을 로드하지 않습니다. 모르고 권한 테스트를 짜면 **막혀야 할 요청이 통과하는데도 테스트가 통과합니다**

# 성능 개선

## 1. 모임 목록 42쿼리 → 2쿼리

**PR** [#81](https://github.com/BonuKoo/Bonapetit/pull/81) · **이슈** [ISS-12](known-issues.md#iss-12)

### 문제 인식

문서에 "10건 페이지당 최대 21회"라고 적혀 있었습니다. **코드를 읽어 센 숫자**였습니다. Hibernate `Statistics`로 재니 두 배였습니다.

| 출처 | 건수 | 원인 |
|---|---|---|
| JPQL | 12 | 목록 1 + `count` 1 + 개설자 조회 **10** |
| 컬렉션 로드 | 10 | `Team.getMembersCount()`가 `members.size()` — **인원수를 세려고 참여자를 전부 로드** |
| 나머지 | 20 | `AccountTeam`의 `@ManyToOne`에 `fetch` 미지정 → **EAGER** |

읽어서 셀 때 놓친 것이 뒤의 둘입니다. **인원수 세기가 컬렉션 로드라는 점**과, **`@ManyToOne` 기본값이 EAGER라 연관을 채우는 SELECT가 따라붙는다는 점**입니다.

### 해결 과정

엔티티를 만들지 않으면 EAGER 연관도 컬렉션도 따라오지 않습니다. **화면이 쓰는 값만 프로젝션했습니다.**

```
42건 → 2건 (목록 1 + count 1)
```

인원수는 `size()`가 상관 서브쿼리로 번역되어 같은 쿼리 안에서 계산됩니다.

곁들여 **전체 건수와 항목 수의 불일치**를 고쳤습니다. 개설자 없는 모임을 목록에서 건너뛰면서도 전체 건수에는 남겨 둬, 10건 페이지에 9건만 나오는 일이 있었습니다. `count` 쿼리에도 같은 조인을 걸었습니다.

죽은 코드 둘(`findPageByKeyword`, `Team.getMembersCount()`)을 지웠습니다. 뒤엣것은 **42건 중 10건의 원인**이라 남겨두면 같은 N+1이 되돌아옵니다.

### 결과

- **쿼리 수만 재면 화면이 깨져도 모릅니다.** 내용도 검증했습니다 — 개설자 닉네임·인원수가 모임마다 정확한지, 검색어가 장소명에도 걸리는지, 전체 건수가 항목 수와 맞는지, 날짜 형식
- 문서의 21건을 42건으로 정정하고 그 이력을 남겼습니다
- **MySQL 실행 계획은 확인하지 못했습니다.** 쿼리 개수는 DB와 무관하지만 상관 서브쿼리의 계획은 다를 수 있습니다. 이 프로젝트는 H2와 MySQL의 계획이 갈려 결론이 뒤집힌 적이 있습니다

## 2. 인가 검사 4쿼리 → 1쿼리

**PR** [#76](https://github.com/BonuKoo/Bonapetit/pull/76) · **ADR** [ADR-008](decisions.md#adr-008-인가-검사를-한곳에-모으고-필요한-두-값만-프로젝션한다)

### 문제 인식

인가 검사는 모임을 다루는 **모든 요청 앞에** 붙습니다. 그래서 비용을 재 두려고 했습니다.

주석에 "쿼리 3건이 1건이 된다"고 적어 두고 `Statistics`로 재니:

```
expected: 1L
 but was: 4L
```

`AccountTeam.account`·`team`이 `@ManyToOne` 기본값 EAGER라 연관을 채우는 SELECT가 붙고, `Team.chatRoom`은 `@OneToOne(mappedBy=…)` 역방향이라 null 확인 SELECT가 또 붙습니다.

### 해결 과정

인가 검사에 필요한 것은 `account_id`와 `is_leader` 둘뿐입니다. **그 둘만 프로젝션했습니다.**

```java
select new TeamMembership(a.account.id, a.isLeader) from AccountTeam a where ...
```

### 결과

- 검사 한 번이 **1쿼리**입니다
- 반환 타입이 엔티티가 아니라 값 객체가 되면서, **호출부가 요청 파라미터 대신 이 값을 쓰도록** 자연스럽게 강제됩니다. 성능 개선이 [문제 해결 1](#1-로그인만-하면-남의-모임을-조작할-수-있었다)의 설계를 거들었습니다
- **같은 원인에 두 번 걸렸습니다.** 여기서 배운 것을 모임 목록에서 못 알아봤고, 거기서 같은 EAGER 함정에 다시 걸렸습니다

## 3. 채팅 병목을 특정했다 — DB가 아니라 팬아웃

**PR** [#83](https://github.com/BonuKoo/Bonapetit/pull/83) · **측정 기록** [부하 측정](experiments/2026-09-chat-send-load.md)

### 문제 인식

성능 개선 후보가 넷 남았는데 **전부 근거가 같은 수준**이었습니다.

| 후보 | 근거 |
|---|---|
| 발송 경로의 계정 SELECT 제거 | 메시지마다 SELECT 1건. **병목인지는 모름** |
| 채팅 인가 쿼리 3 → 2 | 쿼리 1건 감소. **효과는 모름** |
| 모임 검색의 선행 와일드카드 LIKE | 인덱스를 못 씀. **실사용 규모를 모름** |
| Pub/Sub 단일 채널 | 방 수에 비례. **다중 인스턴스가 아님** |

넷 중 무엇을 고를 근거가 없었습니다. 그리고 `application-prod.yml`의 Tomcat 스레드 50 · Hikari 20은 **"k6 재측정 후 조정" 주석만 달린 잠정값**이었습니다. 이 프로젝트에는 부하 수치가 하나도 없었습니다.

### 해결 과정

**STOMP를 기본 지원하는 부하 도구가 없습니다.** k6·Gatling·JMeter 모두 프레임을 수작업으로 조립해야 해서, `WebSocketStompClient` 기반 하니스를 직접 만들었습니다.

진입 장벽은 성능이 아니라 **인증**이었습니다. 소셜 로그인은 스크립트로 통과할 수 없고, 폼 로그인은 주체를 식별하지 못했습니다([ISS-09](known-issues.md#iss-09)). 테스트 스코프에만 존재하는 로그인 경로를 만들되 **우회 범위를 최소로 잡았습니다** — `/test-only/**`에만 걸리는 체인을 앞에 두고, 핸드셰이크 인가는 실제 필터 체인을 지나게 뒀습니다. 그것까지 우회하면 측정 경로가 실제와 달라집니다.

1차 측정에서 동시 사용자 10 → 20에 p50이 256ms → 1,707ms로 뛰었습니다. 그런데 **원인이 갈리지 않았습니다.** 후보 둘(팬아웃 / 생성기가 같은 JVM인 측정 환경)이 **전달 건수를 따라 같이 움직이는 교란변수**였기 때문입니다.

**보낸 건수를 고정하고 전달 건수만 바꾸면 갈립니다.**

| 시나리오 | 보냄 | 전달 | p50 |
|---|---|---|---|
| 한 방 20명 | 600 | **12,378** | **277 ms** |
| 20방 1명씩 | 600 | 622 | **23 ms** |
| 구독 없음 | 600 | 0 | — |

### 결과

- **같은 600건인데 지연이 12배입니다.** 팬아웃이 원인입니다
- **고칠 대상이 두 번 바뀌었습니다.** 1차에서 "DB가 병목이 아니다"(인메모리 H2인데도 포화), 2차에서 "차이는 전부 전달 쪽"이 나오면서, 원래 1순위였던 **발송 경로 SELECT 제거가 맨 뒤로** 갔습니다
- **최적화하지 않을 근거도 생겼습니다.** 지금 수치는 "한 방 20명"이라는 임의의 조건에서 나왔습니다. 식사 모임이 4~6명이라면 전달량은 1/4 이하이고 **최적화할 대상 자체가 없습니다.** 다음에 필요한 것은 코드가 아니라 **실제 모임당 인원 분포**입니다
- **절대 수치로는 못 씁니다.** 생성기와 서버가 같은 JVM이라 클라이언트 비용이 섞입니다. 상대 비교용입니다

# 이번 작업에서 반복된 것

**읽어서 센 것과 실측이 네 번 갈렸습니다.**

| 대상 | 읽어서 | 실측 | 결정 |
|---|---|---|---|
| 인가 검사 쿼리 | 1건 | **4건** | 프로젝션으로 1건 |
| 모임 목록 쿼리 | 21건 (문서 기재) | **42건** | 프로젝션으로 2건 |
| 공지 검색 조인 | 카테시안 곱 의심 | **정상** | 고치지 않음 |
| 채팅 병목 | 발송 경로 DB | **팬아웃** | 우선순위 재배치 |

뒤의 둘은 **"고치지 말라"는 결론**이었습니다. 성능 작업에서 "무엇을 고칠까"만큼 "무엇을 안 고쳐도 되나"가 중요한데, 측정 없이는 후자를 말할 수 없습니다.

**결함을 고칠 때마다 수정을 임시로 되돌려 테스트가 실패하는지 확인했습니다.** 통과만 하고 회귀를 못 잡는 테스트를 걸러내려는 것이었는데, 매번 값을 했습니다.

**문서가 틀린 것도 네 곳 나왔습니다.** ISS-12의 쿼리 수, ISS-11의 두 서술, `UR-03`·`UR-12`의 "충족" 표기입니다. 전부 정정하고 이력을 남겼습니다.
